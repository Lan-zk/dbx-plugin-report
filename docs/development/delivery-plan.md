# 开发计划（阶段 / 轮次 / 验证）

> 关系：[roadmap.md](roadmap.md) 定义**做什么、到哪儿算完成**（里程碑范围、退出条件、决策门）；本文件定义**怎么推进**（阶段与轮次切分、每轮节拍、验证与证据、协作边界）。两处冲突以 roadmap 为准。
> 进度基准（2026-10-22）：**P0 原型阶段进行中**（原型 v1 已出，待确认）；M0 未开始。
> 估算仍是「1 名熟悉前端与 SQL 的开发者」的 T 恤粗估，不是承诺。D1–D5 未拍板前不承诺 M1 及以后的排期（[decisions.md:111](../product/decisions.md)）。

## 1. 三层结构

```
里程碑 M0–M4      范围与退出条件（roadmap.md），跨度 1–10 天，含决策门
  └ 阶段 Phase    可独立演示的成果面；本计划新增 P0 原型阶段
      └ 轮次 Round 1 个可验证目标 + 1 个可见成果 + 1 组证据 + 1 次裁决
```

不直接按里程碑排期的原因：里程碑跨 5–10 天，期间看不到可裁决的东西；而工作流要求每轮以「可运行增量 + 可验证质量 + 真实反馈」为进展依据。轮次控制在 **0.5–2 天**，让每次交付都能被您看到并改方向。

## 3. 轮次协议（每轮固定节拍）

**六步**：① Round brief → ② 方案设计（短设计；改变架构/数据模型时才写 ADR）→ ③ 最小垂直切片实现 → ④ 质量验证 → ⑤ 交付报告 → ⑥ 裁决（continue / adjust / stop）。

**Brief 必填字段**（写进任务板，不单独建文档）：

| 字段 | 要求 |
|---|---|
| 目标 | 一句话，可验证（能被截图、命令或清单证明） |
| 范围 | 明确「做」与「不做」，列出允许改动的路径 |
| 依赖 | 前序轮次、决策门、需外部确认的点 |
| 验收 | 逐条可判定，附验证命令或检查方式 |
| 证据 | 需要落盘的内容（截图路径、命令输出、真机版本） |
| 回滚 | 失败时如何撤回（原型阶段＝删文件；骨架后＝revert 本轮提交） |

**报告必填字段**：Changes / Verification（命令 + 环境 + 日期）/ Documentation（同步了哪些文档）/ Remaining Issues / Next（下一轮建议）。缺证据的轮次不视为完成。

**完成定义（DoD）**：目标达成且证据可复跑 → 文档同步 → 决策点已记录 → Lead 复核过 diff。原型轮的 DoD 额外要求「真实渲染检查」（截图或人工走查），不接受「代码写完即完成」。

**每轮产出一份记录**：`docs/development/records/<date>-round-<id>-<slug>.md`，内容＝该轮 brief 的结论版 + 证据链接（截图只放路径，不放业务数据）。

## 4. P0 原型阶段（进行中）

目标：把 5 个屏幕的信息层级、交互入口、失败文案、样本语义定在纸面上，作为 M1 的实现依据；**原型代码不进产品包**，但 token 与组件 CSS 直接演进为 `ui/styles/`。

| 轮次 | 内容 | 产出 | 状态 |
|---|---|---|---|
| P0-1 | 原型契约：宿主 token 镜像、组件类、场景切换器、mock 数据、索引页 | `prototype/tokens.css`、`app.css`、`proto.js`、`mock.js`、`index.html` | 已完成 |
| P0-2 | 五屏实现（3 人并行，写作用域互斥）：工作台+数据集 / 报表+看板 / 状态与错误 | `prototype/screens/*.html` | 进行中 |
| P0-3 | 渲染验证：无头浏览器逐屏逐场景截图、暗色对照、溢出与对比度检查；按清单修正 | 截图证据 + 修正提交 | 待开始 |
| P0-4 | 您走查并逐条裁决（含「需要确认的五个点」）；需长期约束的登记为 ADR | 评审清单签字结论 + 新增 ADR/待定项 | 待开始 |

**出口条件**：① 5 屏在 1280×800 与暗色下均可正常渲染；② 每条产品不变量在原型中都有可见落点（样本语义、无导出、另存为、逐卡时间、无 cancel、口径漂移）；③ 评审清单无「未解释的空白」；④ 未决点已登记为决策项（D 门或 ADR），不留在口头。

**原型的边界**：不连宿主、不跑真实 SQL、不读真实连接；mock 数据只用于展示语义；不引入构建链。详见 [prototype.md](prototype.md)。

## 5. M0 骨架（1–3 天，4 轮）

沿用 [first-slice.md](first-slice.md) 的闭环：打开 → 执行固定 SQL → 渲染 → 另存 JSON → 重开 → 再执行。

| 轮次 | 目标 | 验收 | 证据 |
|---|---|---|---|
| R0-1 工程与真机空壳 | `dbx-plugin create` 生成工程，Vite+Vue 跑起来，真机安装并看到空白工作台 | 插件中心可安装；`window.dbxPlugin` 与 `capabilities.dataApi` 可见；无 CSP/postMessage 报错 | 版本号、安装截图、控制台无错误 |
| R0-2 取数链路 | 选连接 → 固定 SQL → `queryData`（maxRows 500）→ 表格渲染 + 截断标注 | 宿主 `truncated` 正确传递并在界面标注；≤4 并发队列可见 | 真机截图 + 运行日志（不含 SQL 字面量） |
| R0-3 文件闭环 | `saveFile` 另存 JSON（取消＝未保存）+ `fileTransfer.pick` 分块打开（含取消/超 5 MiB/非法 JSON 分支） | 6 步闭环走通；三条失败分支各有状态与出口；句柄关闭无泄漏 | 真机录屏/截图 + 打开分支清单 |
| R0-4 图表与布局 spike | ECharts 6 按需 vs 轻量 SVG 的包体/首屏/主题跟随；gridstack 14 试 20 卡帧率 | 给出选型结论与包体积数据；H7–H9 各项有结论（[tech-stack.md](tech-stack.md) §7） | 打包体积对比 + 帧率记录 |

M0 出口＝acceptance M0-1…M0-10 全部签收 + `records/<date>-m0.md` 的 go/no-go。此前不得对外承诺 MVP。

## 6. M1–M4 轮次骨架（决策门通过后细化为任务书）

- **M1**（4 轮）：① 文档格式 v0.1 + Zod 校验 + 另存/打开；② 数据集与字段契约（`basis` 哈希、transport、精度）；③ 报表视图 table/bar + 样本语义 + 错误码全链路（含 ABANDONED 与口径 stale）；④ 2 名作者演练 + 修正。
- **M2**（4 轮）：① gridstack 集成 + 布局持久化 + 键盘入口；② 逐卡刷新队列/部分失败保旧/逐卡时间；③ 过滤器定义与显式映射；④ 20 卡性能与主题 a11y 收口。
- **M3**（2 轮）：① 候选 schema + 校验 + 审阅 UI；② V4 评估集跑分，达标则保留、未达标移除 AI 承诺。
- **M4**（3 轮）：① PG 方言 profile + 黄金语料；② 安全回归 V8（含抓包与负例）；③ 签名打包 + 商店审核 + SPDX/NOTICE。

每个轮次的具体任务书在**进入该阶段时**写，不在现在虚构细节；M1+ 的范围仍受 D1–D5 与 roadmap 复议条件约束。

## 7. 并行与写作用域（多 agent 协作规则）

- **单写者原则**：共享契约文件（`prototype/tokens.css`、`app.css`、`proto.js`、`mock.js`，将来的 `src/core/types`）先冻结再分发；谁要改，先广播再改。
- **写作用域互斥**：每轮 brief 列出 allowed paths；同一文件的并行写视为冲突，不是合并。
- **验证者独立**：渲染/测试/契约核对的角色不改业务代码，只出报告，避免「自己验证自己」。
- **Lead 复核**：合并前看 diff + 跑验证命令；不接受「子代理说完成」。
- **Git**：一轮一次提交，提交前确认工作区无他人未完成改动；原型阶段不提交进产品包，也不进发布产物。

## 8. 验证与证据（三分法）

| 维度 | 问题 | 证据形式 | 门槛 |
|---|---|---|---|
| 产品有效性 | 作者愿不愿意用、能不能闭环 | 作者演练记录、原型走查结论 | M1 起每阶段一次演练 |
| 功能正确性 | 数字对不对、截断是否被当完整 | 黄金用例（V2/V3、A01–A16、PG P01–P07）、单测 | 逐项通过；错误结果不得标「完整」 |
| 工程可靠性 | 真机跑不跑得动、安全边界守不守 | 真机检查点（acceptance）、性能数据、V8 安全回归 | 真机为准；单测绿不等于集成通过 |

硬规则：没跑过的命令不算验证；证据写进 `records/` 时附命令、环境、日期；难度大而不能验证的项明确写「未验证」并说明原因。

## 9. 变更控制

1. 范围变化：先改 [decisions.md](../product/decisions.md)（ADR 或 D 门）→ 再改 [roadmap.md](roadmap.md) → 才进入轮次；顺序不可反。
2. 新增能力必须先过[硬边界检查表](../README.md)（不新增宿主 API、不加凭据旁路、不把截断当完整、不引入 sidecar/CDN/遥测）。
3. 单轮内发现范围变大：停手，把这轮按「可交付的最小切片」收尾，剩余部分登记为下一轮，不延长本轮。
4. 原型阶段的返工是预期成本：原型改一处，比实现改一处便宜一个数量级；因此 P0 不追求「做得快」，追求「改得动」。

## 11. 风险与止损

| 风险 | 早期信号 | 动作 |
|---|---|---|
| 原型确认拖延导致实现返工 | P0-4 超过 2 天未裁决 | 只冻结已确认的屏，未确认屏降级为 M1 内的迭代项 |
| 真机数据路径与 dev-host 假设不符 | R0-1/R0-2 真机报错 | 当日停轮、记录复现步骤、按源码核查宿主契约，不猜 |
| 宿主限制（8 MiB / 5000 行 / 60 s）导致体验不可接受 | 演练中出现「想要完整数据」 | 不改语义去迎合，改为明确文案 + SQL 侧聚合建议 |
| 多 agent 并行写冲突 | 同一文件被两人改 | 立即冻结该文件，由 Lead 单点合并 |
| 图表库包体/性能不达标 | 首屏 >1 s 或包体超预算 | 回退轻量 SVG，图表能力降级并记录 |
| 范围被「顺手做掉」 | 轮次 diff 超出 allowed paths | 当轮回滚超范围部分，另立轮次 |

## 12. 需要您裁决的最小清单

1. **P0 原型是否通过**：哪些屏可以直接进入实现，哪些点要改（见 prototype 评审清单）。
2. **D1/D2 是否拍板**：决定 M1 是否能开工（若暂不拍板，默认停在 M0，不外扩）。
3. **D4 是否现在定**（首发库、≤20 卡、手动刷新）：M1 范围冻结前需要。
4. 是否同意「原型确认 → M0 → M1」这个顺序不变（当前计划按此推进）。
