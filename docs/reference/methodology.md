# 方法论：如何得出并维护这些结论

> 目的：后续 agent 不要退化成“看竞品/凭感觉/信博客”。所有结论必须可追溯、可复核、可推翻。

## 1. 证据分级

| 标记 | 含义 | 要求 |
|---|---|---|
| **F（Fact）** | 源码/一手规范可直接核对的事实 | 给路径 + 行号 + 基线 commit；最好附命令 |
| **I（Inference）** | 由 F 推导的判断/裁决 | 写清推导链；可被新证据推翻 |
| **H（Hypothesis）** | 未运行验证的假设 | 写验证方案、负责人、期限；不得当事实引用 |

规则：

- 博客、README 宣传、竞品功能列表只能作为线索，不能单独支撑 F。
- “版本号支持”不等于“能力可用”；以能力探测/实测为准。
- 没有证据的结论标 H，不悄悄升级成 F。
- 外部资料固定版本/commit/日期；星数、排名只作背景。

## 2. 分析顺序（本次使用）

1. **先读宿主合同**：manifest schema、Host API、权限白名单、数据/元数据/文件/AI 限制、安全模型。
2. **从硬限制反推边界**：先确定“做不到什么”，再确定“能做什么”；不先列竞品功能。
3. **写范围三栏**：MVP / 后续 / 明确不做；每项写理由与复议条件。
4. **设计验证顺序**：walking skeleton → 单竖切 → 组合 → AI → 发布；每步有退出/止损。
5. **独立复核**：抽查关键行、跑宿主契约测试、用独立数据库客户端比对、让第二人复现。
6. **沉淀**：F/I/H 分标；更新证据索引与基线；把未决项写成决策门。

## 3. 方法工具箱

| 方法 | 用途 | 本项目的用法 |
|---|---|---|
| Walking skeleton | 最早暴露集成风险 | M0：真机最小闭环，1–3 天 |
| 契约测试 | 证明宿主行为，不证明插件 | DBX 155 项 Vitest；升级回归 |
| 黄金语料 + 独立比对 | 数据正确性 | SQLite `sqlite3`、PG `psql` 对照 |
| 威胁模型（STRIDE 简化） | 安全边界 | 资产/边界/威胁/控制/测试表 |
| 竞品 commit 快照 | 产品结构参考 | Evidence/Metabase 固定 commit，不复制 |
| AI 评估集 | 防“感觉能用” | 40 正常 + 20 对抗；固定模型/提示/词典 hash |
| 标准对照 | 沙箱/许可/SQL 语义 | WHATWG sandbox、CSP、SPDX、各库方言文档 |
| 决策记录（ADR） | 防范围漂移 | 每个关键裁决写理由/替代/复议条件 |

## 4. 外部验证

- **安装/运行**：真机安装 `.dbxp`，不只看构建成功。
- **宿主行为**：跑 DBX 契约测试；核对能力探测与文档。
- **数据正确性**：独立客户端比对，含精度/时区/NULL/截断。
- **安全**：抓包、CSP 日志、负例、代码审计；不只看“没报错”。
- **许可/商店**：SPDX/NOTICE、签名校验、商店审核（H7 未验证）。
- **用户**：2 名目标作者演练，不用开发者代替。

## 5. 文档维护

1. 任何结论变更，先改证据索引/基线，再改结论文档；避免“结论更新、证据过期”。
2. DBX 升级：固定新 commit → 重跑契约测试 → 重核行号 → 更新 `docs/README.md` 基线。
3. 未决问题进入 [product/decisions.md](../product/decisions.md)；不要埋在正文。
4. 里程碑记录写环境/命令/观察/结论；失败也记录，防止重复踩坑。
5. 每季度/每次大版本复核：范围、限制、竞品快照、AI 门槛是否仍成立。

## 6. 反模式（禁止）

- 把竞品功能清单当需求（“Superset 有，所以我们也做”）。
- 把 README/博客当能力证明，不读源码/不实测。
- 把版本号当能力（“1.4 支持”但端/配置不同）。
- 用“以后可能需要”引入抽象/扩展点/后端。
- 在里程碑里悄悄扩大范围，或把未验证的 AI/图表说成已支持。
- 用“测试全绿”替代真机集成；用“没报错”替代安全验证。
- 把截断/失败结果包装成“完整/最新”。
